**Release Blockers المتبقية:** PR-H01 وPR-H03 إلى PR-H07. كما يلزم حسم PR-M01 وترقية المسارات المتأثرة قبل تعريض أي نقل MCP شبكي؛ المشروع الحالي يستعمل stdio محليًا ولا يثبت الفحص قابلية استغلال النشرات في مسار العميل الحالي. يُعالج رصد التشغيل وحماية البيانات وحصص العملاء والتحقق Linux ضمن بوابة إطلاق متكاملة، ولا يُستعاض عنها بنجاح pytest.

التدرج المقترح: أولًا الهوية/إلغاء المفتاح المنكشف؛ ثانيًا التخزين والاستعادة والذرّية؛ ثالثًا تنظيف السجلات والحصص والمراقبة والاعتماديات؛ رابعًا معالجة القبول وتقييم OpenAI المصرح به؛ خامسًا Linux و restore/rollback واختبار وصولية وحمل أطول. بعد ذلك مراجعة إطلاق جديدة بدليل إغلاق كل مانع، لا موافقة تلقائية مسبقة.

## المرحلة الأولى: إصلاح تسجيلات الزوار — 2026-11-03

السبب الجذري كان مجموعة `visitors` تراكمية بلا آخر نشاط أو انتهاء؛ فُحص حد 64 على العدد التاريخي، لا التسجيلات الصالحة. وكان حد 128 محادثة سيمنع إعادة الاستخدام لاحقًا حتى بعد تنظيف الزوار لو بقي محسوبًا على كامل الأرشيف. اختبار إعادة الإنتاج قبل الإصلاح فشل فعلًا عند الزائر 65؛ محفوظ في `evidence/visitor_sessions_before_test.txt`.

أصبح لكل تسجيل وقت نشاط من ساعة monotonic، وعدّاد عمليات وملكية محادثات. الإعداد `SMARTSUPPORT_VISITOR_IDLE_SECONDS=1800` في بيئة عملية الخادم يحدد الخمول الافتراضي بـ30 دقيقة؛ القيم غير الموجبة وغير المحدودة تُرفض. يجري التنظيف عند تسجيل زائر، أو دخول عملية جلسة، أو استدعاء `cleanup_expired_visitors()`؛ لا يوجد مؤقت خلفي. مجرد فتح تبويب بلا طلبات لا يجدد النشاط.

فحص الانتهاء وحجز هوية الطلب وقبول الزائر تجري تحت قفل السجل نفسه. تظل الهوية محجوزة طوال الطلب، بما فيه انتظار قفل المحادثة وSQLite وMCP والموافقة، ويُجدد النشاط بعد اكتماله. يُحمى أيضًا عامل ما زال يعالج طلبًا بعد انتهاء مهلة مستدعيه. يُسحب تسجيل الخامل فقط، ثم يُغلق عامله خارج الأقفال. المعرف المنتهي يُرفض ولا ينقل ملكية أي محادثة إلى زائر جديد؛ تُرفض كذلك مصادفة توليد معرف مرتبط بمحادثات محتفظ بها.

حد الزوار يبقى 64 تسجيلًا صالحًا. حد 128 محادثة يحسب محادثات التسجيلات الصالحة مع حجوزات الإنشاء قيد التنفيذ، ويحرر الحجز عند الفشل. لا يُحذف أي كائن محادثة أو رسالة أو قاعدة أو سجل، ولا تُصفّر حصص SQLite أو مطالبات الموافقة. لا تغييرات في منطق OpenAI أو MCP أو الذاكرة أو حدود الكلفة أو واجهة المستخدم.

أضيفت 19 حالة اختبار بعد احتساب معاملات الاختبارات: الخمول الافتراضي والإعدادات والحد الدقيق وتجديد القراءة؛ منع القراءة والإرسال والموافقة والاستعادة بالمعرف المنتهي؛ حفظ الملفات والبيانات؛ قبول 64 فقط من 96 محاولة متزامنة قبل الانتهاء وبعده؛ حماية الطلب الجاري والمنتظر والعامل الخلفي؛ الإغلاق خارج القفل؛ إعادة استخدام السعة مع حفظ 128 محادثة؛ الحجز المتزامن وتحريره عند الفشل؛ وبقاء حصص الاستخدام ومطالبات الموافقة.

كشف أول تشغيل كامل عائقًا مستقلًا: أرشيف `smartsupport-ai.zip` المحلي دخل فحص النصوص وأحدث `UnicodeDecodeError`. أُضيف استثناء لهذا الاسم فقط في `.gitignore` واختُبر استبعاده من التوزيع؛ لم يُحذف الأرشيف أو يُفتح أو يُعدّل، ولم يُخفف ماسح الأسرار.

التحقق النهائي الفعلي: `RUN_LIVE_OPENAI=0 .venv/Scripts/python.exe -m pytest -q --junitxml=reports/evidence/visitor_sessions_pytest.xml` أعطى **294 ناجحًا، 0 فاشل، 2 متجاوزين** في 123.75 ثانية؛ المتجاوزان اختبار API المدفوع واختبار Linux. أُبقي دليل التشغيل الكامل الأول ذي فشل الأرشيف في `evidence/visitor_sessions_initial_full_pytest.xml`. نُقّحت سلاسل مفاتيح الاختبار الاصطناعية في مخرجات JUnit فقط. تطابقت SHA-256 للسجلات الخمسة وقاعدة المتجر الأصلية مع لقطة ما قبل التغيير؛ الملخص في `evidence/visitor_sessions_verification.json`. لم يُنفذ أي طلب OpenAI مدفوع.

كانت النتيجة وقت المرحلة الأولى أن التسجيل داخل العملية ويفقد عند إعادة التشغيل؛ حدّثت المرحلة الثانية هذا القيد بسجل خاص واستعادة إثباتية موضحة أدناه. تبقى المخاطر: لا مصادقة إنتاجية أو حصص مشتركة بين المثيلات؛ يستطيع 64 زائرًا نشطًا إشغال السعة؛ ولا يضع إصلاح المرحلة الأولى حدًا لحجم المحادثات المحتفظ بها في الذاكرة أو القرص. عمر عامل MCP الخامل (3 دقائق) مستقل عن عمر تسجيل الزائر.

## المرحلة الثانية: استعادة آمنة للحالة — 2026-11-03

هذا القسم يحدّث قيود الاستمرارية في نتيجة المرحلة الأولى أعلاه، ولا يغير نتائج التدقيق التاريخية أو سجلاته.

**سبب الفقد:** `visitors` و`conversations` ورسائل العرض والاختيار والملكية و`Conversation.result` تعيش في backend المخزن عبر `st.cache_resource`، ويعيش إثبات الواجهة في `st.session_state`. إعادة عرض Streamlit العادية تبقيها غالبًا؛ إعادة إنشاء المورد أو عملية Python تفقدها. عامل MCP و`Agent._tasks` والطابور و`Future` والتاريخ التنفيذي وcall IDs وحجوزات أدوات المهمة المؤقتة تعيش في الذاكرة أيضًا. كانت ملفات المتجر و`conversation_memory` والموافقات و`web_controls` وJSONL والتكلفة اليومية تبقى إذا بقي القرص، دون سجل ملكية آمن لإتاحتها لزائر بعد فقد الذاكرة.

**الحفظ الجديد:** `web_sessions.sqlite3` في مجلد تشغيل الويب يحفظ تسجيل الزائر وانتهاءه وإلغاءه، وبصمة سر استعادة مستقل، وملكية المحادثة والعميل وسياق MCP وأرشيف العرض المنقح ونتيجة المهمة وحالتها وبصمة الموافقة وموعد انتهائها وبصمات محاولات الشكوى. لا يحفظ سر الاستعادة الخام أو grant أو reasoning أو طابورًا قابلًا للتنفيذ. معاملات SQLite (`BEGIN IMMEDIATE` و`synchronous=FULL`) تثبت بدء المهمة قبل dispatch، وتثبت حالتها النهائية والرسائل معًا. UUID فريد لـ`web_task_id` يربط المهمة بسجلها؛ معرّف مهمة الوكيل داخل النتيجة يظل كما يستخدمه التدقيق وسجل التكلفة. لا تغيير في مخطط متجر العملاء أو بروتوكول MCP أو الأدوات الست أو سياسة ask_on_write أو حدود الكلفة.

**إثبات الاستعادة:** `create_browser_session()` يصدر معرفًا وسرًا مستقلًا عشوائيًا بـ256 بت. يُخزن SHA-256 للسر فقط، وتُقارن البصمة بمقارنة ثابتة الزمن. `restore_visitor()` يتطلبهما معًا، ويتحقق من الصلاحية والملكية قبل تحميل محادثات هذا الزائر وحده؛ لا يكفي معرف الزائر أو المحادثة أو `TrustedSession.session_id`. هذه صلاحية جلسة متصفح مجهول، وليست هوية حساب عميل. تعرض الواجهة السر في حقل password للحفظ الخاص، ولا تضعه في URL أو JSONL أو سياق النموذج أو MCP. عند فقد حالة المتصفح يلزم إدخاله يدويًا مع المعرف؛ وعند إعادة إنشاء المورد فقط يمكن استخدام الإثبات الباقي في حالة المتصفح لاستعادة العرض. لا fallback بمعرف أو باختيار اسم عميل.

**العمر والتنظيف:** تبقى مدة الخمول الافتراضية 1800 ثانية من المرحلة الأولى وحماية العمليات والعمال الجارية. تُحفظ صلاحية مطلقة للاستعادة بين العمليات، وتُفحص دون تمديد عند بدء الخادم. الانتهاء والإلغاء لا يزولان بإعادة التشغيل؛ رصد انتهاء صلاحية صحيح يثبت الإلغاء قبل الرفض، وتراجع الساعة عن وقت آخر النشاط يرفض الاستعادة. العملية الحية تستعمل ساعة monotonic وحجوزاتها؛ طلب استعادة آخر لا يلغي عملية جارية تجاوزت TTL أثناء العمل. التنظيف يشمل التسجيلات غير المحملة من SQLite، ولا يحذف أي محادثات أو رسائل أو ملفات. العد يحفظ أيضًا حصة الزوار والمحادثات غير المستعادة كي لا يصفر restart الحدود.

| الحالة المحفوظة | ما يحدث عند الاستعادة |
| --- | --- |
| `completed` | تعاد النتيجة المسجلة والسياق للمالك فقط؛ لا تحقق تلقائي بالنموذج ولا إعادة أداة |
| `failed` أو `cancelled` | تعاد الحالة المسجلة دون تنفيذ؛ نجاح مهمة أخرى أو نتيجة أداة سابقة لا يُفترض |
| `pending_approval` | تتحول إلى `cancelled / approval_restart_required` وتزال إمكانية الاستكمال؛ يلزم طلب جديد ومراجعة وموافقة جديدتان |
| `running` | تتحول إلى `failed / interrupted` مع `outcome_unknown` و`usage_complete=False`؛ قد تكون كتابة أو فاتورة حدثت بالفعل، ولا يدعي التطبيق نفيها أو نجاحها |
| ملفات نسخة قديمة بلا سجل إثبات، أو سر مفقود، أو تسجيل منتهٍ | لا استعادة؛ تبقى الملفات ولا تُنسب لهوية جديدة |

**منع التكرار والموافقات:** `request_id` مرتبط بالمحادثة وبصمة الإدخال؛ إعادة الطلب نفسه تعيد نتيجته فقط، وتغيير محتواه يرفض. تعطي الواجهة كل إرسال جديد مهمة جديدة، ولا تعيد مهام SQLite تلقائيًا. المطالبة بالموافقة انتقال أحادي من pending إلى running تحت معاملة، مع مهلة 120 ثانية وربط دقيق للتفاصيل؛ تُرفض التفاصيل المعدلة أو المهلة المنتهية. يتحقق العامل أيضًا من تطابق التفاصيل ومن مهلة monotonic قبل إصدار grant؛ يبقى فحص grant وربطه بالعميل والجلسة والأداة والمحتوى واستهلاكه داخل MCP كما كان. تُحجز بصمة `create_ticket` المطابقة تمامًا ضمن الزائر والعميل قبل إصدار grant، وتبقى عند الفشل أو النتيجة المجهولة، حتى عبر محادثات جديدة لنفس الزائر. هذا منع محافظ قد يرفض محاولة لم تنفذ فعلًا؛ لا تُمسح البصمة تلقائيًا ولا يُطلب تغيير المحتوى لتجاوزها. الرفض لا يمنح صلاحية كتابة جديدة.

**التزامن وملكية العملية:** `DirectoryLease` يستخدم قفل نظام التشغيل (Windows `msvcrt` أو POSIX `flock`) طوال ملكية backend للمجلد. يُرفض مالك ثانٍ بـ`busy`؛ لا يجوز لمورد جديد اعتبار عمل مورد حي منقطعًا. لا يُغلق backend أثناء عملية جارية، ويبقى القفل إذا ظل عامل يعالج طلبًا بعد مهلة المستدعي. انهيار العملية يحرر قفل OS دون حذف ملف القفل؛ عندئذ فقط يصالح المالك الجديد حالات المهمة محليًا دون إعادة إرسال. هذا نموذج مالك واحد على نظام ملفات محلي، وليس تنسيقًا موزعًا.

**التكلفة:** سجل `DailyCostLedger` ومساره وحدوده لم يتغيروا. تحفظ الاستعادة حقول الاستهلاك المعلومة في النتيجة ولا تصفر الكلفة. حجوزات API غير المحسومة تبقى محسوبة في السجل اليومي عبر restart كما كانت، حتى لو تعذر ربط نتيجة منقطعة بالفاتورة النهائية. عدم اكتمال القياس ليس تكلفة صفرية مؤكدة. استمرار الحماية يتطلب بقاء ملف السجل نفسه وإعداد مساره؛ لا نقل تلقائي لحجوزاته أو محوها.

**المخاطر المتبقية بعد المرحلة الثالثة:** سر مسروق يمنح صلاحية جلسة المتصفح إلى أن تنتهي/تلغى؛ لا توجد مصادقة إنتاجية أو وسيلة استرجاع سر مفقود. يلزم تقييد ACL لمجلد التشغيل وحماية SQLite والنسخ، فالنصوص غير مشفرة. لا أرشفة محدودة أو سياسة حذف جديدة، ولا ضمان لبقاء `/tmp` على Render أو للعمل عبر NFS/مضيفين متعددين. ما زال ملف الموافقات وملف المتجر منفصلين، لذلك لا توجد ذرّية مشتركة ولا يمكن ضمان exactly-once عند فقد/استرجاع نسخة واحدة دون الأخرى. عند انقطاع بعد إرسال الكتابة تبقى الحالة pending/unknown إلى أن تفحص المصالحة سجل المتجر؛ لا يُعاد إرسالها تلقائيًا. ملفات النسخة القديمة لا تملك إثبات ترحيل، لذا لا تُستعاد. أول ترقية من backend القديم تتطلب إيقافًا مخططًا بعد انتهاء الطلبات؛ لا استئناف لعمله الحي. لم يُعد تشغيل خادم المستخدم أو ينشر المشروع أثناء هذه المهمة.

## المرحلة الثالثة: ذرّية الكتابة ومصالحة الموافقات — 2026-11-03

**التسلسل السابق:** كان `approval_store.consume_approval()` يستهلك grant في ملف approvals، ثم يستدعي خادم MCP `database.create_ticket()` أو `save_memory()` في ملف المتجر. انقطاع العملية بين الخطوتين قد يترك الموافقة مستهلكة بلا كتابة؛ والانقطاع بعد commit المتجر قد يمنع العميل من معرفة النتيجة. كانت حماية المحاولات في جلسة الويب حجزًا سابقًا للتنفيذ، وليست إيصالًا ذريًا موثوقًا للكتابة.

**التنفيذ:** لكل موافقة مفتاح ثابت SHA-256 مشتق من الإصدار والعميل والجلسة والأداة والحمولة المعتمدة canonical. سجل الموافقات يحفظ الربط وبصمة المحتوى وحالات `pending` و`committed` و`failed` و`unknown` مع مهلة lease. عند قاعدة المتجر، يوضع سجل idempotency الفريد ونتيجة `create_ticket` أو `save_memory` في معاملة `BEGIN IMMEDIATE` نفسها التي تكتب الأثر. يعيد المفتاح نفسه والحمولة نفسها النتيجة المسجلة دون أثر جديد؛ وأي عدم تطابق في الهوية أو العملية أو البصمة يُرفض. لا يتغير مخطط أدوات MCP أو `ask_on_write`؛ المفتاح داخلي ولا يقبله النموذج.

عند بدء MCP تُفحص العمليات القابلة للمصالحة. بعد أي نتيجة مجهولة، تستعلم المصالحة عن سجل المتجر قبل السماح بقرار جديد: وجود سجل مطابق يعيد النتيجة، عدم القدرة على قراءة المتجر يبقي الحالة `unknown` ويمنع التنفيذ، وسجل `pending` ذي lease سارية يبقى pending. بعد انتهاء lease، غياب سجل المتجر يحسم العملية إلى `failed`؛ وأي إعادة تنفيذ تتطلب موافقة جديدة. لا يعاد استدعاء OpenAI أو MCP تلقائيًا بعد restart. جدول `write_attempts` القديم محفوظ للترقية لكنه لم يعد مرجع idempotency.

**حدود الضمان:** ملفا SQLite منفصلان، فلا ندعي معاملة ذرّية مشتركة. ما يضمنه الكود محليًا هو ذرّية الأثر وسجل نتيجته داخل قاعدة المتجر، مع سجل موافقات منفصل ومصالحة تعالج انقطاع الرد. استعادة نسخة احتياطية واحدة دون الأخرى أو فقد الملفات أو تشغيل عدة مضيفين على تخزين غير مدعوم قد تترك `unknown` أو اختلافًا؛ الإجراء الآمن حينها fail-closed ومراجعة المشغل، لا إعادة الكتابة. لا توجد مصادقة إنتاجية ولا ضمان distributed exactly-once.
