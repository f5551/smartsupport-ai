# تحسين استهلاك التوكنز — SmartSupport AI

التاريخ: **2026-11-03**. لم يُنفذ أي استدعاء OpenAI مدفوع أثناء هذا العمل. التغييرات تخص حدود الوكيل وإدارة السياق والتكلفة؛ لا تعديل خادم MCP أو بيانات المتجر أو قواعد صلاحياته أو إصدار/استهلاك الموافقات. تبقى موانع الإنتاج الأخرى الواردة في تقرير الجاهزية خارج نطاق هذا التحسين.

## تحليل الاستهلاك السابق

رُوجعت `agent.py` و`cost_tracker.py` و`config.py`، وأُعيدت قراءة السجل الحقيقي `traces/live_success_1.jsonl`. المزوّد OpenAI، النموذج الفعلي `gpt-5.4-mini-2026-03-17`، طلبان، إدخال **1056**، إخراج **72**، cached **0**، وتكلفة محسوبة من usage **0.001116 دولار**، و`final_answer` بعد `search_faq`. هذه **عينة مهمة واحدة**، ولا تكفي للحكم بأن الاستهلاك مرتفع عمومًا أو لحساب متوسط مهام الإنتاج.

مصادر الزيادة المحتملة التي ثبتت في بناء الطلبات:

- إعادة التعليمات وتعريفات الأدوات في كل طلب. كل تعريف يدخل سياق النموذج؛ راجع [توثيق Function Calling](https://developers.openai.com/api/docs/guides/function-calling). التعريفات الست أبقيت متاحة حتى لا يكسر تحسين مبني على تخمين النية الوظائف العربية أو الذاكرة أو الموافقات.
- تعليمات مطولة وتكرار احتياطات شبيهة في وصف الأدوات. اختُصرت الصياغة مع بقاء فصل الهوية، وعدم الثقة بالمخرجات، ومنع الكتابة بلا موافقة، وعدم ادعاء نجاح غير مؤكد.
- طبقة الويب كانت تجمع آخر رسائلها في نص مستخدم واحد، فيصعب على الوكيل تمييز السؤال الحالي وتطبيق حد الرسائل. أصبحت تمرر تاريخًا منظّمًا مستقلًا.
- نتائج أدوات تصل إلى 64000 بايت كانت تدخل السياق كاملة؛ تراكم FAQ أو ذاكرة طويلة يرفع الطلب التالي.
- لم يوجد منع لتكرار القراءة نفسها في حلقة النموذج. الحد السابق 8 جولات و 512 إخراجًا وإعادة 429 واحدة كانت تسمح بإنفاق أوسع.
- الحجز السابق اعتمد بايتات UTF-8 +1024 بدل محلل رموز محلي، ما قد يبالغ في الحجز وخصوصًا العربية. الحساب النهائي من usage باستخدام Decimal كان صحيحًا، وبقي دون تغيير في `cost_tracker.py`.

## العد المحلي وإدارة السياق

`token_limits.py` يستخدم `tiktoken==0.14.0` و o200k، من ملف vocabulary محلي في `assets/tokenizer/` مُطابق لبصمة المكتبة الرسمية؛ ترخيص MIT محفوظ معه. نُزل الجدول مرة من CDN الرسمي أثناء التجهيز، وليس عبر OpenAI API. لا تنزيل شبكة أو استدعاء endpoint عد الرموز أثناء تشغيل الوكيل.

الطريقة: عد JSON مختصر للتعليمات والسياق وتعريفات الأدوات، ثم إضافة 256 رمزًا كبنية احتياطية و 8 لكل عنصر تاريخ و 16 لكل أداة. **هذا تقدير محلي محافظ وليس `input_tokens` الرسمي أو برهانًا رياضيًا على سقف 3000 في فاتورة المزوّد.** لا يوجد معامل `max_input_tokens` مماثل لـ max_output في طلب Responses هنا. قد تختلف البنية الداخلية أو tokenizer نموذج مستقبلي. راجع [توثيق عد الرموز](https://developers.openai.com/api/docs/guides/token-counting). إذا أبلغ الرد input أعلى من الحد، تسجل تكلفته ويُوقف الاستمرار قبل أدواته أو طلب إضافي.

تُحذف الرسائل الحوارية الأقدم عند الحاجة، ويبقى السؤال الحالي. لا تُقص function_call و function_call_output أو reasoning ولا تُغيّر call_id، حتى لا تصبح متابعة Responses غير صالحة. كل هذه العناصر تدخل عد الإدخال؛ حد 6 يخص الرسائل الحوارية فقط، مع سقف 3 أدوات و 4 طلبات يحدان تبادلات البروتوكول. إذا لم تتسع التبادلات الحالية يخرج `input_token_limit` بدل إرسال سياق ناقص أو توسيع السقف.

نتائج FAQ تُختصر بإزالة عناصر كاملة أقل ترتيبًا، مع عدد العناصر المحذوفة؛ لا قص لشروط السياسة وسط الإجابة. في بيانات الذاكرة والوصف/items الطويلة، يُسمح بمقتطف نصي موسوم بـ`truncated` و`truncated_fields` وتنبيه عدم استنتاج المحذوف، وتبقى معرفات الإيصالات وحالاتها سليمة. إن تعذر الاحتواء يعود `RESULT_TOO_LARGE` بصيغة JSON صالحة. لا يغيّر ذلك النص الأصلي في SQLite أو عملية حفظ وافق عليها المستخدم، ولا يحذف الذاكرة. يوضح المحاكي أيضًا أن الذاكرة المعروضة مقتطف. لا نستطيع ضمان جودة إجابة نموذج حي عن محتوى مختصر دون تقييم حقيقي منفصل.

## التكرار والتزامن والموافقات

- في الدفعة نفسها، قراءة متطابقة تستخدم ناتجًا محفوظًا داخل المهمة مع إخراج مربوط بكل call_id، فلا يُعاد MCP بلا داعٍ.
- عبر جولتين للنموذج، طلب قراءة مطابق دون كتابة يوقف الحلقة بـ`duplicate_tool_call`، بدل تمويل مزيد من الجولات المتكررة.
- أي كتابة تبطل مخبأ القراءة. اختبار MCP الفعلي `load_memory → save_memory` بموافقة موثوقة `→ load_memory` أثبت ظهور النص الجديد؛ لم تُستخدم ذاكرة قديمة بعد الحفظ.
- تكرار الكتابة نفسها داخل المهمة لا يولد كتابة ثانية. لا تغيير في grant أو payload أو شروط الملكية، ولا إعادة تلقائية لكتابة مجهولة النتيجة.
- `Agent.run(..., request_id=...)` يقبل معرف إرسال من التطبيق الموثوق فقط؛ ثمانية استدعاءات متزامنة بالمعرف نفسه نفذت طلب نموذج واحدًا. ربط المعرف بمحتوى آخر يُرفض. هذا منع تكرار داخل كائن الوكيل/جلسة الخادم، **وليس idempotency دائمًا عبر إعادة تشغيل أو أجهزة مختلفة**. عدم توفير معرف جديد لكل إرسال مقصود قد يعيد نتيجة الإرسال السابق؛ لا نزيل تكرار النص وحده كي تبقى إعادة الاستعلام المقصودة ممكنة.

## سجل التكلفة اليومي

`daily_cost.py` منفصل عن متجر MCP وموافقاته. المسار الافتراضي `data/daily_api_cost.sqlite3`، أو `DAILY_COST_DB_PATH` على قرص دائم موثوق. يحتفظ بمعرف طلب عشوائي، ويوم القبول، وحجز/تكلفة وحالة؛ لا رسائل أو هوية عميل أو مفتاح. التوقيت **Asia/Riyadh**، والوحدة integer تساوي 10^-12 دولار مع تقريب محافظ للأعلى، بدل حساب money بـ float.

كل قبول يجري داخل `BEGIN IMMEDIATE` مع `synchronous=FULL`: يجمع committed والحجوزات غير المسوّاة ثم يضيف الحجز ذريًا إن كفت الحصة. بعد الرد يسوي من حساب `CostTracker` الفعلي؛ الخصم cached يأتي من usage الصحيح. طلب لم يُرسل بسبب فشل التدقيق يُلغى حجزه المعروف أنه غير مستهلك. فشل اتصال/مهلة أو usage مجهول يبقي الحجز، حتى عبر إعادة تشغيل أو انتقال اليوم، ولا توجد مهلة تنظفه وتفتح إنفاقًا جديدًا تلقائيًا.

إذا تجاوز الاستهلاك الفعلي الحجز، تُحفظ القيمة الأعلى كما هي ويُمنع الاستمرار؛ لا نخفي التجاوز أو نعرض حدًا مطلقًا للفاتورة. فشل تخزين السجل يخرج `budget_storage_error` ولا يرسل API. Fake لا يستهلك الحصة الحقيقية. يدعم ذلك عمليات متعددة على الجهاز/القرص نفسه، **لا مثيلات على أجهزة بملفات منفصلة**؛ تحتاج بيئة موزعة عدادًا مركزيًا. ويجب أن يكون الملف على volume دائم عند النشر؛ ميزة محلية لا تحول `/tmp` إلى تخزين دائم.

العداد يسجل الطلبات منذ تفعيل هذه الميزة، وليس فاتورة حساب OpenAI أو استيرادًا تلقائيًا لكل تشغيل تاريخي. القياس السابق في JSONL يبقى دليلًا مستقلًا؛ الحجوزات المجهولة تحتاج مصالحة موثوقة من المشغّل، دون منح النموذج حق تعديلها أو تصفيرها.

## مقارنة قبل وبعد دون API مدفوع

حُفظت طلبات FAQ القديمة قبل تعديل الكود في [لقطة قبل التحسين](evidence/token_optimization_before.json). أعيد السيناريو نفسه مع FakeOpenAI وناتج FAQ حتمي مطابق؛ **n=1**، وليست عينة أحمال إنتاج. وُحدت call_id العشوائية قبل العد، واستُخدمت طريقة العد المحلية نفسها للجانبين. يمكن إعادة المقارنة من [الحزمة](evidence/token_optimization_benchmark.py)، والنتيجة في [JSON](evidence/token_optimization_comparison.json).

| تقدير الإدخال المحلي للطلب الأول |1068|961|

انخفض **التقدير المحلي للإدخال 9.90%** في هذه العينة، لا usage رسمي مقاس. ظل طلبا FAQ لأن أحدهما يطلب الأداة والثاني يستخدم نتيجتها لإنتاج الإجابة؛ لم يُلغَ دور النموذج النهائي لادعاء توفير. أرقام usage الثابتة في Fake ليست دليل توفير. JSON المقارنة يتضمن envelope تكلفة افتراضيًا بالأسعار الرسمية مع افتراض بلوغ كل رد max_output؛ هذا حد تخطيطي افتراضي وليس تكلفة فعلية أو فاتورة.

لم يُسجل زمن تنفيذ السيناريو القديم، لذلك **لا ندّعي تسارعًا مقاسًا قبل/بعد**. يوجد زمن محلي للسيناريو الجديد في JSON يشمل بدء محلل الرموز، ولا يمثل استدلال OpenAI. لم تُنفذ API حية بعد التحسين، وبالتالي **تكلفة API الحقيقية بعد التحسين غير مقاسة**. يبقى القياس السابق 1056/72 و 0.001116USD كما هو؛ لا يقارن مباشرة بتقدير هذه الحزمة، إذ تختلف تعريفات الأدوات وطريقة العد وهوامشها.
